# Requirements Document

## Introduction

The Overseer imports a file it does not own. `packages/overseer/src/generated/microservice-registry.ts` is written by the Registry_Generator into a Framework_Singleton's own `src/`, and the Overseer's `packages/overseer/src/index.ts` statically imports it. That static import is worth keeping — it is what makes a wrong generated export shape a compile error rather than a `Cannot read properties of undefined` at run time — but it is only possible today because the Build_System and the project it builds are the same tree. Code generation into an installed `node_modules` package is not possible, so a scaffold whose tooling is consumed rather than forked cannot keep the generated registry inside the tooling. The registry has to move to the side that owns the selection.

Three facts make the move narrower than it sounds:

1. **The injection seam already exists.** `boot({ microserviceRegistry, env })` is a pure pipeline over an injected `MicroserviceRegistry`, performing no `process.exit` and no stderr write. `startServer(app, port)` binds the socket. Neither needs to change shape.
2. **One module holds every process effect.** `packages/overseer/src/index.ts` says so in its own header: it is the only place that statically imports the generated registry, writes to stderr, calls `process.exit`, and binds the socket. Everything that must move is in that one file.
3. **`packages/contracts/` is already a separate package** exporting the shared type surface plus a `./testing` subpath.

So this feature moves the entrypoint module out of the Overseer package into a consumer-owned package, takes the static import of the Generated_Registry with it, and leaves the Overseer's remaining modules as a library the consumer's entrypoint imports by package name. Four consequences follow and are in scope because they are the point. The Registry_Generator writes into the consumer's tree instead of the framework's. The root `prepare` script that copies the Registry_Template retires, together with the Registry_Template itself, which means the load-bearing question the template answered — how a fresh clone typechecks before anything is generated — needs a different real answer, and gets one here. The `[scope:template]` check that spec `config-driven-discovery` added as a declared stopgap retires, exactly as that spec's Accepted Imprecisions said it would. And the container entrypoint path, which today names the Overseer's compiled `dist/index.js`, becomes the consumer entrypoint's path, so `Dockerfile.template`, the Image_Assembler's staging, `scripts/start.js`, and the Dev_Supervisor's restart target all follow it.

One further relocation lands here because it is the same shape of problem: `packages/contracts/testing/arbitraries.ts` emits values and needs `fast-check`, while `contracts` sits in a consumer's `dependencies`. The arbitraries move to `packages/build-tools/`, which is already a development-only dependency, and `contracts` keeps types only.

The feature changes where code lives and which module imports which. It changes no routing, no toggle name, no toggle semantics, and no selector semantics. The Overseer mounts the same routers at the same paths, the Generated_Registry names the same microservices with the same scoped specifiers, and `npm run ci` passes. Four of the recorded Pre_Change_Baseline fixtures do change, and each change is a named consequence of the two relocations rather than a behavioural drift; Requirement 14 says which, why, and how narrowly.

Explicitly **out of scope**, each the subject of a later spec: removing the bootstrap build (`scripts/common-startup.js` and `scripts/build.js` stay — the bootstrap exists partly because `build-workspaces` is compiled output, which stops mattering only after the tier split); publishing any package to any registry; re-shaping the repository into platform, fixture, and example tiers; shipping tsconfig, eslint, or prettier presets; the wiring generator; and the CI/release split. The Image_Assembler's always-staged `contracts` special case also stays: it becomes an ordinary dependency arriving through a production install only once the packages are genuinely published, which this feature does not do.

Provenance: this feature implements decision D6 of `.kiro/steering/platform-split.md` in full together with the arbitraries relocation of D8. Those citations record where the decisions came from; every behaviour this document requires is stated here in its own terms and reads correctly with that record unloaded.

## Glossary

Terms carried over unchanged from the `config-driven-discovery` spec — Build_System, Project_Directory, Project_Config_File, Project_Config, Effective_Config, Config_Parser, Config_Loader, Config_Diagnostic, Filesystem_Validation, Configured_Scope, Scope_Default, Valid_Scope, Discovery_Root, Root_Default, Valid_Root_Path, Consumer_Category, Consumer_Package, Microservice_Package, Common_Package, Spa_Package, Framework_Singleton, Package_Discovery, Dependency_Specifier, Repo_Invariant_Checker, Registry_Generator, Selector, Selected_Microservices, Tsc_Project, Bundler_Project, Load_Bearing_Setting, Root_Manifest, Workspace_Coverage, Emit_Script, Exclusion_List, Synthesized_Tree, Payload_Tree, Steering_Documents — keep their meanings and are not redefined here. The terms below are new, or are redefined because this feature changes what they name.

- **ProjectContext**: The per-run derivation of the Effective_Config that every Build_System component receives: the Configured_Scope, the three Discovery_Roots, the Entry_Root, the four Framework_Singletons with their scoped names, and the scoped-name composer. The single value a run threads, introduced by the `config-driven-discovery` feature and extended by this one with the Entry_Root and the Entry_Point_Path.
- **Entry_Package**: The consumer-owned npm workspace package that holds the Entry_Module and receives the Generated_Registry. It is neither a Framework_Singleton nor a member of any Consumer_Category. It is the package the container image and every local run invoke by path.
- **Entry_Root**: The Project_Directory-relative path of the Entry_Package's directory, declared by the `entry` key of the Project_Config or taken from the Entry_Root_Default.
- **Entry_Root_Default**: The Entry_Root a run uses when the Project_Config declares no `entry`: the string `app`.
- **Entry_Module**: The committed TypeScript source at `<Entry_Root>/src/index.ts`. The process-effect shell: it statically imports the Generated_Registry, calls the Overseer_Library's boot pipeline, writes every diagnostic to stderr, calls `process.exit` on failure, and binds the HTTP socket. Consumer-owned: committed source no Build_System component reads, rewrites, or validates the contents of.
- **Entry_Point_Path**: The Entry_Module's compiled path, `<Entry_Root>/dist/index.js`. The path the container `CMD`, `scripts/start.js`, and the Dev_Supervisor each spawn, and the path the Image_Assembler stages the Entry_Package to satisfy.
- **Generated_Registry**: The generated TypeScript module at `<Entry_Root>/src/generated/microservice-registry.ts` that statically imports the Selected_Microservices by their scoped package names and exports one registry entry per Selected_Microservice. Fills the role `packages/overseer/src/generated/microservice-registry.ts` fills before this feature. Generated output, gitignored, never committed.
- **Registry_Export**: The single binding the Generated_Registry exports: `microserviceRegistry`, typed `MicroserviceRegistry` imported from the scoped `contracts` package. The name and type the Entry_Module imports, so a generator that emitted a different name or shape is a compile error.
- **Registry_Template**: The committed empty registry at `packages/overseer/src/generated/microservice-registry.template.ts`, which the root `prepare` script copies into the generated registry's location so a fresh clone has a compilable registry before anything is built. Retired by this feature.
- **Template_Copy_Step**: The root `package.json` `prepare` script that performs the Registry_Template copy. Retired by this feature.
- **Overseer_Library**: The Overseer package after this feature: a library whose public API is its barrel at `packages/overseer/src/index.ts`, exporting the boot pipeline, the server binder, and their types. It imports no generated file and holds no `src/generated/` directory.
- **Registry_Generation_Step**: An invocation of the Registry_Generator for the run's Selector. Every path that compiles or typechecks the Entry_Package performs one before that compilation.
- **Build_Sequence**: The single ordering primitive whose statements every Order_Producing_Path derives its order from (`packages/build-tools/src/build-sequence.ts`). Before this feature its statements are: `contracts`, `build-tools`, the Common_Packages in calculated order, the Selected_Microservices, the Overseer, the test-only Framework_Singletons, and the Spa_Packages as a trailing bundler phase.
- **Entry_Statement**: The Build_Sequence statement this feature adds, whose single member is the Entry_Package.
- **Order_Producing_Path**: A Build_System entry point that derives a build order from the Build_Sequence and then builds or watches the packages in it: the ordered repository build, the image build, and the dev session.
- **Project_List**: The ordered set of package directories an Order_Producing_Path builds for one Selector, derived from the Build_Sequence.
- **Microservice_Identifier**: A Microservice_Package's directory name under the microservice Discovery_Root, which is the sole declaration of the identifier.
- **Microservice_Path**: The HTTP path a Microservice_Package's module exports, at which the Overseer mounts that package's router.
- **Prerequisite_Edge**: A pair of packages recording that the second's compilation reads the first's compiled output, over which the Build_Sequence's Verification_Pass rejects any order placing a package ahead of one of its own prerequisites.
- **Verification_Pass**: The check the Build_Sequence runs over every produced order and its Prerequisite_Edges, failing the run rather than spawning a build over an unsound order.
- **Required_Dependencies**: The set of Consumer_Packages and framework packages an Image_Tree stages because a root of the dependency walk reaches them by following `dependencies` keys carrying the Configured_Scope.
- **Image_Assembler**: The Build_System component that stages everything a runtime image contains into a single tree (`packages/build-tools/src/image-tree.ts`).
- **Image_Tree**: The staged tree the Image_Assembler writes and the container runtime stage copies once.
- **Dev_Supervisor**: The Build_System component behind `npm run dev` that keeps an incremental build watching and restarts the spawned server process against recompiled output (`packages/build-tools/src/dev-supervisor.ts`).
- **Scope_Template_Check**: The `[scope:template]` check of the Repo_Invariant_Checker, which reads the Registry_Template and reports one violation when it declares no scoped import specifier or declares one under a scope other than the Configured_Scope. Retired by this feature.
- **Arbitraries_Module**: The shared `fast-check` arbitraries and test-support helpers at `packages/contracts/testing/arbitraries.ts` and their entry point `packages/contracts/testing/index.ts`, reached today through the specifier `<Configured_Scope>/contracts/testing`. Relocated by this feature.
- **Retired_Testing_Specifier**: The module specifier `<Configured_Scope>/contracts/testing`, which no source names after this feature.
- **Pre_Change_Baseline**: The repository state at the commit immediately preceding this feature, the reference for every "unchanged behaviour" comparison.
- **Baseline_Recording**: One committed fixture under `packages/integration-tests/baseline/` recording an observable of the Pre_Change_Baseline, produced by `scripts/record-baseline.js`.

## Requirements

### Requirement 1: The consumer-owned Entry_Package

**User Story:** As a project author, I want the module that selects and wires my microservices to live in my own tree, so that the tooling generates into my project instead of into itself.

#### Acceptance Criteria

1. THE Build_System SHALL locate the Entry_Package at the Entry_Root, being the Project_Directory-relative path the Project_Config's `entry` key declares or the Entry_Root_Default `app` when the Project_Config declares no `entry` key, SHALL take a declared value exactly as it appears in the JSON string, applying no trimming, no separator normalisation, and no case normalisation, and SHALL resolve that path against the Project_Directory exactly as it resolves a Discovery_Root.
2. THE Build_System SHALL recognise exactly three top-level keys of the Project_Config — `scope` holding a string, `roots` holding an object, and `entry` holding a string — SHALL keep the three recognised keys of `roots` (`microservice`, `common`, `spa`) and their Root_Defaults unchanged, SHALL treat `entry` as optional, and SHALL support no environment-variable override of the Entry_Root.
3. THE Build_System SHALL declare the Entry_Root_Default as a literal in exactly one module, the same module that declares the Scope_Default and the three Root_Defaults, and SHALL derive every other use of the Entry_Root from the ProjectContext.
4. THE Config_Parser SHALL accept a declared `entry` value if and only if that value is a Valid_Root_Path, and IF a declared `entry` value is a string that is not a Valid_Root_Path, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:entry-path]` — one per rejected value, not one per violated condition — that names the key `entry`, reproduces the rejected value exactly as declared, and names every Valid_Root_Path condition the value violates rather than only the first, and SHALL return no Effective_Config for that input.
5. IF the `entry` key is present and holds a JSON value that is not a string, THEN THE Config_Parser SHALL apply no Valid_Root_Path validation to it, SHALL report exactly one Config_Diagnostic tagged `[config:shape]` that names the key path `entry`, the JSON type found, and the JSON type required, SHALL report no `[config:entry-path]` diagnostic for the same key, and SHALL exclude the `entry` value from the criterion 6 comparisons while substituting no Entry_Root_Default for it, so that one wrong-typed `entry` yields exactly one diagnostic.
6. IF the Entry_Root is equal to, lies inside, or contains one of the three Discovery_Roots of the Effective_Config, the directory holding the Framework_Singletons (`packages`), or one of the four Framework_Singleton package directories — each relation decided code point for code point, case-sensitively and with no normalisation, equality being string equality, "lies inside" meaning the Entry_Root begins with the other path followed by a single `/`, and "contains" meaning the other path begins with the Entry_Root followed by a single `/` — THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:entry-overlap]` per offending pair of the Entry_Root and one colliding path, at most eight such diagnostics, each naming the `entry` key, the Entry_Root, the colliding path, and which of the three relations holds, SHALL order those diagnostics by ascending code-point comparison of the colliding path, and SHALL return no Effective_Config for that input, so that the Entry_Package cannot be placed inside the platform's own directory or inside a discovered category; and THE Config_Parser SHALL apply this criterion to an Entry_Root that took the Entry_Root_Default and to a Discovery_Root that took its Root_Default, while excluding from these comparisons every `entry` or `roots` value already rejected by criterion 4, by criterion 5, or by the `[config:root-path]` check, so that no `[config:entry-overlap]` diagnostic names an already-rejected value.
7. THE Config_Parser SHALL list `entry`, `roots`, and `scope` in ascending code-point order as the recognised top-level keys of every `[config:unknown-key]` diagnostic it reports at the top level.
8. THE Build_System SHALL treat the Entry_Package as a workspace package for Workspace_Coverage, requiring exactly one entry of the Root_Manifest `workspaces` array to match the Entry_Root, and SHALL classify it as neither a Framework_Singleton nor a member of any Consumer_Category.
9. THE Package_Discovery SHALL yield the same set of Consumer_Packages with the Entry_Package present as it yields without it, so that the Entry_Package appears in no Consumer_Category's discovered set and in no Microservice_Registry.
10. THE Entry_Package SHALL declare a `package.json` whose `name` is the Configured_Scope followed by `/` and the last path segment of the Entry_Root, whose `type` is `module`, which declares the four standard scripts (`build`, `test`, `lint`, `typecheck`), and which declares `dependencies` naming the scoped `overseer` package and the scoped `contracts` package.
11. THE Entry_Package SHALL declare no dependency naming a Microservice_Package, because the Selected_Microservices are Selector-dependent and the dependency resolver rejects a manifest naming a Microservice_Package, and THE Build_System SHALL keep rejecting such a manifest with its existing `[deps:peer]` diagnostic and grant the Entry_Package no exemption.
12. THE Build_System SHALL require no `main` and no `types` field of the Entry_Package and SHALL apply no barrel validation to it, because nothing imports the Entry_Package by name and the container invokes it by path.
13. THE Entry_Package SHALL declare a `tsconfig.json` satisfying every Load_Bearing_Setting the Repo_Invariant_Checker verifies for a shipping Tsc_Project, being `composite` and `declaration` each `true`, `outDir` resolving to its own `dist` directory, and `rootDir` resolving to its own `src` directory.
14. THE Build_System SHALL treat the Entry_Package as a Tsc_Project, making it a root of the single selective `tsc --build`, and SHALL NOT treat it as a Bundler_Project.
15. THE repository SHALL place its own Entry_Package at `app/`, taking the Entry_Root_Default, and SHALL commit `app/package.json`, `app/tsconfig.json`, and the Entry_Module as tracked source.
16. THE Config_Parser SHALL decide every `entry` validation of criteria 4, 5, and 6 from the input string and the Effective_Config's other declared values alone, performing no filesystem access for the `entry` value, and SHALL report no Config_Diagnostic concerning the Entry_Root's existence, its being a directory, or its holding a `package.json`, so that one input string yields the identical Config_Diagnostic list whether or not the Entry_Package is present on the filesystem.
17. IF the Config_Loader reports a `[config:entry-path]` or a `[config:entry-overlap]` Config_Diagnostic, THEN THE Build_System SHALL terminate the run with a non-zero exit status before any Package_Discovery, SHALL perform no Registry_Generation_Step, derive no build order, and assemble no Image_Tree, and SHALL leave the bytes of any already-present Generated_Registry and of any already-present generated `Dockerfile` unchanged.

### Requirement 2: The Entry_Module owns every process effect

**User Story:** As a project author, I want one small file I own to be the thing that starts my server, so that the platform stays a library I call rather than a process that calls me.

#### Acceptance Criteria

1. THE Entry_Module SHALL statically import the Registry_Export from the Generated_Registry by a relative specifier inside the Entry_Package, and SHALL pass that value to the Overseer_Library's boot pipeline as its injected registry.
2. THE Entry_Module SHALL import the boot pipeline and the server binder from the scoped `overseer` package by that package name, and SHALL import no module of the Overseer package by a relative path and no module of any package by a path reaching inside that package's `src` or `dist` directory.
3. THE Entry_Module SHALL be the only module of the Entry_Package and of the Overseer_Library that writes to the process standard error stream, calls `process.exit`, or binds an HTTP socket, and SHALL be the only tracked non-test source of the repository that statically imports the Generated_Registry.
4. IF the boot pipeline reports a failure, THEN THE Entry_Module SHALL write every reported message to standard error, one message per line in the order the boot pipeline reported them and each terminated by a single `\n`, SHALL bind no socket, and SHALL terminate the process with exit status 1.
5. IF binding the HTTP socket fails, THEN THE Entry_Module SHALL write to standard error exactly one message naming the port and the underlying failure, terminated by a single `\n`, SHALL write no line of the registered-microservice table, and SHALL terminate the process with exit status 1.
6. WHEN the boot pipeline succeeds and the socket is bound, THE Entry_Module SHALL write to standard output one table-header line, then one line per registry entry in the order the entries appear in the Generated_Registry, each carrying that entry's identifier, its mounted path, and whether its toggle evaluated as enabled, then one line naming the listening port, and SHALL write nothing to standard error.
7. THE Entry_Module SHALL produce standard-output and standard-error text byte-identical to the text the Pre_Change_Baseline's `packages/overseer/src/index.ts` produces for the same registry, environment, and failure, including every bracketed message prefix, every leading space of a table line, the order of the lines, and the single `\n` terminating each line.
8. THE Entry_Module SHALL derive the type of its registry binding from the Generated_Registry's own declaration rather than asserting a type over a dynamic import, so that a Generated_Registry exporting a differently named binding or a binding of a different shape fails the Entry_Package's own `tsc` compilation.
9. WHEN the Entry_Package is compiled, THE compilation SHALL resolve every import specifier of the Generated_Registry, so that a Selected_Microservice whose module does not satisfy the registry's declared type fails that compilation rather than failing at run time.
10. THE Build_System SHALL read no content of the Entry_Module, SHALL write no content into the Entry_Module, and SHALL apply no validation to the Entry_Module's source beyond the checks the Repo_Invariant_Checker applies to every package of the repository.

### Requirement 3: The Overseer becomes a library

**User Story:** As a project author, I want the Overseer to be a package I import, so that the platform holds no file my build generates.

#### Acceptance Criteria

1. THE Overseer_Library SHALL export from its barrel at `packages/overseer/src/index.ts` the boot pipeline function, the server binder function, and every type each of those two functions names in its signature.
2. THE Overseer_Library SHALL export from its barrel every symbol the Entry_Module imports from it and every symbol the Overseer package's own test suite imports from a module other than by relative path, and SHALL treat its barrel as its sole stable public API.
3. THE Overseer_Library SHALL declare `main` as its compiled barrel `./dist/index.js` and `types` as `./dist/index.d.ts`.
4. THE Overseer_Library SHALL contain no module that imports a generated file and SHALL hold no `src/generated/` directory, and no import declaration and no dynamic `import()` call of any module of the Overseer_Library SHALL carry a specifier containing the path segment `generated` or a final segment whose base name is `microservice-registry`, each comparison made code point for code point and case-sensitively.
5. THE Overseer_Library SHALL perform no `process.exit` call, no write to the process standard error stream, and no HTTP socket bind in any module.
6. THE repository SHALL delete `packages/overseer/src/generated/` together with the Registry_Template it contains, and SHALL remove the `.gitignore` entry naming the retired generated registry path while adding one naming the Generated_Registry's path under the Entry_Root.
7. THE Build_System SHALL stage the Overseer_Library into an Image_Tree as a real directory at `node_modules/<Configured_Scope>/overseer` holding its `package.json` and its compiled `dist` and no other file, SHALL stage no `src` directory of it, and SHALL no longer stage it at its package directory, because the Entry_Module now imports it by package name rather than the container invoking it by path.
8. THE Overseer_Library SHALL keep every routing, toggle-evaluation, and validation behaviour of the Pre_Change_Baseline: the same mount order, the same duplicate-path rejection, the same toggle variable names and accepted values, and the same message text for every reported failure.

### Requirement 4: What the Registry_Generator emits, and where

**User Story:** As a project author, I want the generated registry written into my project, so that selecting a different set of microservices changes a file I can read next to my own code.

#### Acceptance Criteria

1. WHEN the Registry_Generator runs, THE Registry_Generator SHALL write the Generated_Registry to `<Entry_Root>/src/generated/microservice-registry.ts`, taking the Entry_Root from the ProjectContext, and SHALL write no file under any Framework_Singleton's directory.
2. THE Registry_Generator SHALL create every absent directory of the Generated_Registry's path before writing, SHALL replace the whole contents of an already-present Generated_Registry rather than appending to it or truncating and extending it, and SHALL leave no partially written Generated_Registry at that path, so that any path reading the file observes either its previous complete contents or the complete new contents.
3. THE Registry_Generator SHALL emit one static import per Selected_Microservice, in the order the Selector resolved them — for the `*` and blank Selector spellings the ascending code-point order of directory name in which Package_Discovery yields the candidates, and for a comma-separated list the order the identifiers appear in that list — each specifier being the Configured_Scope followed by `/` and that microservice's directory name, and SHALL derive each identifier and each specifier from the directory name rather than from the name the microservice's own manifest declares.
4. THE Registry_Generator SHALL emit the Registry_Export as a single exported binding named `microserviceRegistry`, typed `MicroserviceRegistry` imported from the Configured_Scope followed by `/contracts`, holding one entry per Selected_Microservice in the criterion 3 order, each entry carrying exactly the fields `identifier`, `module`, and `sourcePackage` in that order, where `identifier` is the microservice's directory name, `module` is the binding that microservice's own emitted static import declares, and `sourcePackage` is that microservice's scoped specifier.
5. THE Registry_Generator SHALL compose every scoped name it emits from the ProjectContext's Configured_Scope, so that for an Effective_Config whose Configured_Scope differs from the Scope_Default no emitted specifier carries the Scope_Default, and SHALL hold no scope literal of its own.
6. THE Registry_Generator SHALL emit a header naming the generator and the Selector it ran for, SHALL emit no reference to the Registry_Template, and SHALL emit in that header no timestamp, no absolute filesystem path, no host name, no user name, and no other value that differs between two runs over the same ProjectContext, Selector, and discovered packages.
7. WHEN the Registry_Generator runs twice for the same ProjectContext, Selector, and discovered packages, THE Registry_Generator SHALL write byte-identical Generated_Registry contents on both runs and SHALL terminate with a zero exit status on both runs, independently of whether a Generated_Registry was present before either run and of what that file contained.
8. IF the Selector resolves to no microservice, or names an identifier matching no discovered Microservice_Package, THEN THE Registry_Generator SHALL fail the run with its existing `[selector:empty]` or `[selector:unmatched]` diagnostic, SHALL terminate with a non-zero exit status, SHALL create no directory of the Generated_Registry's path, SHALL write no Generated_Registry, and SHALL leave the bytes of an already-present Generated_Registry unchanged.
9. THE Registry_Generator SHALL emit, for the Selector and the Configured_Scope of every run, a Generated_Registry whose import-specifier sequence, entry sequence, per-entry field set, and per-entry field values are equal to those the Pre_Change_Baseline emits for the same Selector and the same Configured_Scope.
10. THE Registry_Generator SHALL write the Generated_Registry encoded as UTF-8 with no byte-order mark, using `\n` as its only line terminator, and ending in exactly one `\n`.

### Requirement 5: Retiring the Registry_Template, and what replaces its guarantee

**User Story:** As a developer on a fresh clone, I want a typecheck to either succeed or tell me exactly which command to run, so that retiring the template does not leave me reading an unresolved-module error.

#### Acceptance Criteria

1. THE Root_Manifest SHALL declare no `prepare` script performing the Template_Copy_Step, and THE Build_System SHALL write no Generated_Registry during `npm install` or `npm ci`.
2. THE repository SHALL contain no Registry_Template and no other committed file whose purpose is to stand in for an ungenerated registry.
3. THE Build_System SHALL perform a Registry_Generation_Step for the run's Selector before it compiles or typechecks the Entry_Package on every path that does so, being the ordered repository build, the `npm start` startup sequence, the `npm run dev` startup sequence, and the container image build stage.
4. THE Entry_Package's own `build` script and its own `typecheck` script SHALL each perform a Registry_Generation_Step before invoking the compiler, so that `npm run build` and `npm run typecheck` in the Entry_Package's directory each succeed on a clone that has never generated a registry, provided the Build_System itself is compiled.
5. IF the Entry_Package is compiled or typechecked while no Generated_Registry is present at its path, THEN THE Build_System SHALL write to standard error exactly one diagnostic naming the absent Generated_Registry path and the command that produces it, SHALL invoke no compiler, SHALL emit no compiled output for the Entry_Package, and SHALL terminate with a non-zero exit status, rather than surfacing only the compiler's unresolved-module error.
6. WHEN `npm ci` followed by `npm run ci` runs on a fresh clone, THE quality gate SHALL complete every composed step with exit status zero, the leading ordered build having performed the Registry_Generation_Step that the later per-package typecheck and lint steps depend on.
7. THE repository SHALL exclude the Generated_Registry from version control and from the container build context, and THE container image build SHALL copy no registry stand-in into the build stage or the production-dependency stage before its install step.
8. THE Build_System SHALL keep the Generated_Registry's path stable for a given Effective_Config across every path that writes it, so that a registry generated by one path is the file every other path compiles.
9. IF the Entry_Package's own `build` or `typecheck` script cannot perform its Registry_Generation_Step because the Build_System's own compiled output is absent, THEN THAT script SHALL write to standard error exactly one diagnostic naming the absent compiled entry point and the repository-root command that produces it, SHALL invoke no compiler, SHALL write no Generated_Registry, and SHALL terminate with a non-zero exit status.

### Requirement 6: Retiring the Scope_Template_Check

**User Story:** As a scaffold maintainer, I want the stopgap check removed the moment the condition it guarded disappears, so that `check:invariants` reports nothing that no longer has a subject.

#### Acceptance Criteria

1. THE Repo_Invariant_Checker SHALL perform no Scope_Template_Check, SHALL read no Registry_Template, and SHALL emit no `[scope:template]` diagnostic for any repository state.
2. THE Repo_Invariant_Checker SHALL keep every other check it performs — Workspace_Coverage, import discipline, Common_Package dependency direction, the build-order-source check, the Load_Bearing_Setting check, and the `[scope:literal]` check — with its existing diagnostic tag, message wording, and reporting order.
3. WHEN `check:invariants` runs over this repository, THE Repo_Invariant_Checker SHALL produce standard-output and standard-error text byte-identical to the text the Pre_Change_Baseline produces and SHALL terminate with exit status zero.
4. THE `[scope:literal]` check SHALL keep scanning `packages/build-tools/src/` and SHALL report no occurrence after this feature, so that the Entry_Root and the Entry_Point_Path introduce no new Scope_Default literal into the Build_System's sources.
5. IF the number of Root_Manifest `workspaces` entries matching the Entry_Root is not exactly one, whether zero or more than one, THEN THE Repo_Invariant_Checker SHALL report exactly one Workspace_Coverage violation naming the Entry_Root and every matching entry it found, SHALL decide the match the same way it decides it for every other workspace package, and SHALL terminate with a non-zero exit status.

### Requirement 7: The entrypoint path follows the Entry_Module

**User Story:** As an operator, I want the container to start the project's own entrypoint, so that the image runs the module that declares the wiring.

#### Acceptance Criteria

1. THE Build_System SHALL derive the Entry_Point_Path in exactly one module as the Entry_Root joined to `dist/index.js` by a single `/`, using `/` as its only separator and applying no normalisation to either part, and SHALL supply it to every consumer through the ProjectContext.
2. THE Build_System SHALL name the Entry_Point_Path, and no Framework_Singleton's compiled path, as the module the container `CMD` spawns, the module `scripts/start.js` spawns, and the module the Dev_Supervisor spawns and respawns.
3. ## Open Questions Deliberately Deferred

- **The decision record's sequencing line is stale about `contracts`.** `.kiro/steering/platform-split.md` sequences "registry inversion and the split of `contracts` into its own published package". `packages/contracts/` is already its own workspace package with its own manifest, its own type surface, and a `./testing` subpath, so there is no split to perform; the only remaining part of D8 this feature can implement is the arbitraries relocation, which it does. The record should be corrected to say so when it is next revised. Nothing in this feature depends on that wording.
- **Whether the runtime library surface becomes a single facade.** This feature exports the existing boot pipeline and server binder from the Overseer's barrel, because both are already the right shape and renaming them would change the Entry_Module for no observable gain. Whether the published package offers one `createOverseer`-style entry point instead belongs to the spec that publishes it.
- **Whether the Entry_Root stays configurable.** This feature makes it a Project_Config key so that no Build_System module holds a second layout literal. When the repository splits into platform, fixture, and example tiers, the example may become its own Project_Directory taking the Entry_Root_Default, at which point the key may be worth keeping for consumers or worth fixing; either way the relocation is a move plus a config edit, not a redesign.
- **Whether a types-only package needs to ship into a runtime image.** Unchanged and still open. `contracts` is built and staged for every Selector exactly as before.

## Accepted Imprecisions

- **A fresh clone has no generated registry until something builds.** Retiring the Registry_Template means an editor opened on a never-built clone reports the Entry_Module's import of the Generated_Registry as unresolved until the first build or the Entry_Package's own `typecheck` runs. The alternative — a committed empty stand-in copied by an install hook — is the template under another name, carries the same scope literal the `config-driven-discovery` feature accepted as an imprecision, and would have to be kept in sync with the generator's export shape by hand. Requirement 5.5's named diagnostic is the mitigation: the failure says which file is absent and which command writes it.
- **The Entry_Package's imports of the Selected_Microservices resolve through workspace symlinks, not through declared dependencies.** Requirement 1.11 forbids the Entry_Package from declaring a Microservice_Package dependency, because the selected set is Selector-dependent and the dependency resolver rejects such a manifest. The Generated_Registry's specifiers therefore resolve through the symlinks npm creates for every workspace, exactly as the Overseer's generated imports resolve today, and the Build_Sequence carries the ordering edges synthetically. A genuine consumer project outside this workspace would declare those dependencies for real; making that work belongs to the spec that publishes the platform.
- **`WORKSPACE_SCOPE` and the Project_Config's `scope` remain independent inputs whose agreement nothing verifies.** This feature changes neither, and adds the same shape of independence for the entrypoint: the generated `Dockerfile`'s `CMD` is written from the Effective_Config the Emit_Script reads, while the image build's own registry generation reads the config inside the build stage. Both read the same committed file, so they agree in practice, and nothing cross-checks them.
- **The `[scope:literal]` check still covers `packages/build-tools/src/` only.** Unchanged from the `config-driven-discovery` feature. The Entry_Module and the Entry_Package's manifest legitimately spell the scope, because npm requires a literal package name and the Entry_Module is consumer-owned source the Build_System does not read.
