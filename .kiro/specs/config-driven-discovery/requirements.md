# Requirements Document

## Introduction

The Build_System assumes that it **is** the repository. Three assumptions are baked into its sources as literals:

1. **The npm scope.** `WORKSPACE_SCOPE = "@microservices"` is declared in `packages/build-tools/src/framework.ts` and reappears as a literal in the Registry_Generator's emitted output, in the committed Registry_Template, and in the Repo_Invariant_Checker's scope-based rules (a Microservice_Package may not import a peer or the Overseer; a Common_Package points downward only). `scripts/rename-scope.sh` exists for exactly one reason: the scope is baked in, so rebranding it means a tracked-file-wide search and replace.
2. **The discovery roots.** `NAMESPACE_CONTAINER` fixes the three directories the Build_System scans as `packages/microservices`, `packages/common`, and `packages/spa`. A project that wants its microservices at `packages/services` cannot say so. The same three literals are repeated as shell literals in `scripts/emit-effective-dockerfile.sh`, which runs before anything is compiled and therefore cannot import them.
3. **The load-bearing TypeScript settings.** The build is a single `tsc --build` over project references, so `composite: true` and `declaration: true` are mandatory, and the Image_Assembler stages `dist/`, so `outDir` must be the package's own `dist/` and `rootDir` its own `src/`. None of this is stated anywhere and nothing verifies it. A package that omits `outDir` emits beside its sources and fails later with a `tsc --build` error that names neither the setting nor the reason.

This feature turns all three into configuration. A Project_Config file declares the project's scope and its three Discovery_Roots; the Build_System reads that file once per run and threads the result through discovery, the Repo_Invariant_Checker, the Registry_Generator, the workspace-coverage check, and the Dockerfile Emit_Script. It also adds the one verification the third assumption needs: a check inside `check:invariants` that reads each Tsc_Project's **resolved** TypeScript configuration and fails fast, naming the offending package, the setting, and the reason it is required.

The feature is deliberately a de-hard-coding refactor plus one new verification, **not a move**. Every default reproduces the present state exactly: scope `@microservices`, roots `packages/microservices`, `packages/common`, `packages/spa`. A project with no Project_Config file at all is valid and behaves as it does today, so this repository keeps building unchanged and every existing quality gate keeps passing. No package moves, no package is published, the generated Microservice_Registry is byte-identical for the default configuration, and the Overseer's runtime behaviour is untouched.

Two consequences fall out of the change and are in scope because they are its point. First, `scripts/rename-scope.sh` retires: a project declares its scope once in one field rather than rewriting every tracked file. Second, the two Build_System tests that assert against the checked-in payload tree — `packages/build-tools/tests/discovery-real-tree.test.ts` and `packages/build-tools/tests/workspace-build-order-real-tree.test.ts` — do so only because they have no other tree to point at; once discovery takes its roots from configuration they can be pointed at a Synthesized_Tree, and the general claims they carry move to property tests over synthesized layouts while the real-tree tests keep the narrower job of catching core-versus-reality drift.

Explicitly **out of scope**, each the subject of a later spec: inverting the generated registry into the consuming project, splitting the platform into published packages, removing the bootstrap build, re-shaping the repository into platform, fixture, and example tiers, shipping tsconfig/eslint/prettier presets (only the *verification* of the four load-bearing settings lands here), the wiring generator, and the CI/release split.

Provenance: this feature implements decision D5 of `.kiro/steering/platform-split.md` in full, together with the verification half of D10 and the per-package placement rule of D11. Those citations record where the decisions came from; every behaviour this document requires is stated here in its own terms and reads correctly with that record unloaded.

## Glossary

- **Build_System**: The tooling that loads the Project_Config, discovers packages, generates the Microservice_Registry, orders the workspace build, derives the Project_List, checks repository invariants, and assembles the container Image_Tree. Concretely `packages/build-tools/` plus `scripts/emit-effective-dockerfile.sh`.
- **Project_Directory**: The directory a Build_System run treats as the root of the project it operates on. Every path the Project_Config declares is relative to it, and every path the Build_System reports is relative to it. It defaults to the process working directory, which for every command documented in `.kiro/steering/tech.md` is this repository's root.
- **Project_Config_File**: The single file `scaffold.config.json`, located directly in the Project_Directory, in which a project declares its Configured_Scope and its Discovery_Roots. It is committed source, not generated output.
- **Project_Config**: The declared contents of the Project_Config_File: a JSON object whose recognised keys are `scope` (a string) and `roots` (an object whose recognised keys are `microservice`, `common`, and `spa`, each a string).
- **Effective_Config**: The fully defaulted, validated configuration one Build_System run operates on: exactly one Configured_Scope and exactly one Discovery_Root per Consumer_Category, with no absent and no optional field. The single value every Build_System component takes its scope and roots from.
- **Config_Parser**: The component that turns the text of a Project_Config_File, or its declared absence, into either an Effective_Config or a non-empty list of Config_Diagnostics. A total function over its input that performs no filesystem access.
- **Config_Serializer**: The component that renders an Effective_Config back into Project_Config_File text.
- **Config_Loader**: The effect shell that reads the Project_Config_File from the filesystem, hands its text to the Config_Parser, applies the Filesystem_Validations, and yields either an Effective_Config or a non-empty list of Config_Diagnostics.
- **Config_Diagnostic**: One reported problem with a Project_Config: a bracketed tag, the JSON key path or category the problem concerns, the offending value, and the reason the value is rejected.
- **Filesystem_Validation**: A Project_Config validation that requires reading the filesystem and therefore belongs to the Config_Loader rather than the Config_Parser: whether a Discovery_Root exists, and whether a Discovery_Root is itself a package.
- **Configured_Scope**: The npm scope of the Effective_Config: the value every scoped package name, every Dependency_Specifier, and every emitted import specifier of the project is expected to carry.
- **Scope_Default**: The Configured_Scope a run uses when the Project_Config declares no `scope`: the string `@microservices`. Declared as a literal in exactly one Build_System module.
- **Valid_Scope**: A string consisting of `@` followed by one or more characters, each a lowercase ASCII letter, an ASCII digit, or a hyphen.
- **Discovery_Root**: The Project_Directory-relative path of the one directory whose direct subdirectories are the packages of one Consumer_Category. Fills the role the fixed Namespace_Container directories fill today. A Discovery_Root is not itself a package and declares no `package.json`.
- **Root_Default**: The Discovery_Root a run uses when the Project_Config declares none for a Consumer_Category: `packages/microservices` for microservice, `packages/common` for common, `packages/spa` for spa.
- **Valid_Root_Path**: A non-empty string that is a relative POSIX path: it uses `/` as its only separator, does not begin with `/`, contains no `\` character, contains no `*` or `?` character, contains no `.` or empty path segment, contains no `..` segment, and therefore names a location inside the Project_Directory.
- **Consumer_Category**: A kind of package a user of the template writes, discovered by location as a direct subdirectory of that category's Discovery_Root. Exactly three: microservice, common, spa.
- **Consumer_Package**: Any package belonging to a Consumer_Category. A Microservice_Package, a Common_Package, or a Spa_Package.
- **Microservice_Package**: A Consumer_Package discovered under the microservice Discovery_Root. Its directory name is its Microservice_Identifier.
- **Common_Package**: A Consumer_Package discovered under the common Discovery_Root: a leaf library imported by package name.
- **Spa_Package**: A Consumer_Package discovered under the spa Discovery_Root: a bundler-built frontend, built through its own `npm run build`.
- **Framework_Singleton**: A package of the scaffold itself, known to the Build_System by name and never discovered. Exactly four: `packages/contracts`, `packages/overseer`, `packages/build-tools`, `packages/integration-tests`. Their directories remain fixed literals in this feature; only their scoped names follow the Configured_Scope.
- **Package_Discovery**: The Build_System component that enumerates the Consumer_Packages of each Consumer_Category and validates each one against its category's manifest contract (`packages/build-tools/src/discovery.ts`).
- **Dependency_Specifier**: A key of a package's `dependencies` that begins with the Configured_Scope followed by `/`.
- **Repo_Invariant_Checker**: The compiled check the root `check:invariants` script runs (`packages/build-tools/src/repo-invariants.ts` via `packages/build-tools/dist/bin/check-repo-invariants.js`). It reports workspace coverage, import discipline, Common_Package dependency direction, and build-order-source violations, and after this feature also Load_Bearing_Setting violations.
- **Registry_Generator**: The Build_System component that writes the Microservice_Registry (`packages/build-tools/src/generate-registry.ts`).
- **Microservice_Registry**: The generated TypeScript module at `packages/overseer/src/generated/microservice-registry.ts` that statically imports the Selected_Microservices and declares one registry entry per Selected_Microservice.
- **Registry_Template**: The committed empty registry at `packages/overseer/src/generated/microservice-registry.template.ts`, which the root `prepare` script copies into the Microservice_Registry's location so a fresh clone has a compilable registry before anything is built.
- **Selector**: The `MICROSERVICES` value: `*` or blank for every discovered Microservice_Package, or a comma-separated list of Microservice_Identifiers.
- **Selected_Microservices**: The Microservice_Packages the Selector resolves to.
- **Tsc_Project**: A package compiled by the TypeScript solution builder: every Framework_Singleton, every Microservice_Package, and every Common_Package.
- **Bundler_Project**: A package built by invoking its own `npm run build`, never a root of `tsc --build`. Every Spa_Package.
- **Load_Bearing_Setting**: One of the four TypeScript compiler settings the Build_System depends on and therefore verifies: `composite` equal to `true`, `declaration` equal to `true`, `outDir` resolving to the package's own `dist` directory, and `rootDir` resolving to the package's own `src` directory. The first two apply to every Tsc_Project without exception, because every Tsc_Project is a root of the single `tsc --build`. The last two — `outDir` and `rootDir` — are verified for every Tsc_Project **except** a Non_Shipping_Singleton, because those two settings exist to pin the output layout the Image_Assembler and the Overseer entrypoint depend on, and a Non_Shipping_Singleton reaches neither: its four reason texts are unchanged in wording, but the `outDir` and `rootDir` reasons do not apply to a package that never ships, so those two settings are not verified for it.
- **Non_Shipping_Singleton**: A Framework_Singleton whose compiled `dist` directory no Image_Tree stages and that no package imports by name, so that no Image_Assembler or Overseer-entrypoint output layout depends on where it emits. Exactly two: `packages/build-tools` and `packages/integration-tests`. The two shipping Framework_Singletons — `packages/contracts`, which is staged into `node_modules/@microservices/contracts` for every Selector, and `packages/overseer`, which is staged at its package directory — are not Non_Shipping_Singletons and are verified on all four Load_Bearing_Settings.
- **Resolved_Tsconfig**: A package's TypeScript configuration as the compiler resolves it, with every `extends` chain applied, so that a value a package inherits from a base configuration is present in the resolved view. Obtainable through `tsc --showConfig` or through the TypeScript compiler API. Distinct from the raw JSON text of the package's own `tsconfig.json`.
- **Tsconfig_Verifier**: The Repo_Invariant_Checker component that reads each Tsc_Project's Resolved_Tsconfig and reports each Load_Bearing_Setting it does not satisfy.
- **Root_Manifest**: The repository root `package.json`, which declares the `workspaces` array, the shared devDependencies, and the `engines` block.
- **Workspace_Coverage**: The Root_Manifest obligation that exactly one entry of the `workspaces` array matches each workspace package directory, which is what npm needs in order to discover the workspaces and create the scoped symlinks. An obligation over the set of entries only; their order carries no meaning.
- **Emit_Script**: `scripts/emit-effective-dockerfile.sh`, which renders the committed `Dockerfile.template` into the generated `Dockerfile`. Dependency-free POSIX sh, run before any install, and therefore unable to import any compiled Build_System module.
- **Manifest_Copy_Block**: The generated block of per-workspace `package.json` `COPY` lines the Emit_Script writes at its anchors.
- **Exclusion_List**: The Emit_Script's set of top-level `packages/<name>` entries that contribute no `COPY` line, currently the literals `integration-tests`, `microservices`, `common`, and `spa`.
- **Scope_Rename_Script**: `scripts/rename-scope.sh`, the POSIX sh script that rewrites the npm scope across tracked files.
- **Synthesized_Tree**: A package layout a test creates for itself, either as in-memory inputs to a pure function or as directories inside an operating-system temporary directory. Never a directory created inside the checked-out repository.
- **Payload_Tree**: The Consumer_Packages checked into this repository: the three microservices, the two common packages, and the one Spa_Package.
- **Pre_Change_Baseline**: The repository state at the commit immediately preceding this feature, the reference for every "unchanged behaviour" comparison.
- **Steering_Documents**: `.kiro/steering/tech.md` and `.kiro/steering/structure.md`.

## Requirements

### Requirement 1: The Project_Config file

**User Story:** As a project author, I want to declare my npm scope and my package locations in one file, so that the tooling adapts to my layout instead of my layout adapting to the tooling.

#### Acceptance Criteria

1. THE Build_System SHALL treat the working directory of the running process as the Project_Directory, SHALL read the Project_Config from exactly one path, `scaffold.config.json` directly inside that Project_Directory, and SHALL search no ancestor directory, no subdirectory, and no alternative filename for it.
2. THE Build_System SHALL treat the Project_Config_File contents as JSON, SHALL recognise exactly two top-level keys, `scope` holding a string and `roots` holding an object, SHALL derive no field of the Effective_Config from any other top-level key, and SHALL support no other configuration format and no environment-variable override of the Configured_Scope or of any Discovery_Root; and THE Build_System SHALL treat recognising exactly two top-level keys as constraining which top-level keys carry meaning and not as requiring either key to be present, each recognised key being optional under criterion 4.
3. THE Build_System SHALL recognise inside the `roots` object exactly three keys, `microservice`, `common`, and `spa`, each holding a string that is the Discovery_Root of that Consumer_Category.
4. THE Config_Parser SHALL treat every recognised key as optional, so that an input declaring no key, only `scope`, only `roots`, or a `roots` object declaring one or two of its three keys yields an Effective_Config in which each undeclared value takes its Scope_Default or Root_Default.
5. IF no filesystem entry exists at the Project_Config_File path, THEN THE Config_Loader SHALL yield the Effective_Config whose Configured_Scope is the Scope_Default and whose three Discovery_Roots are the three Root_Defaults, and SHALL report no Config_Diagnostic.
6. THE Config_Loader SHALL yield, for a Project_Config_File whose contents are the JSON text `{}`, an Effective_Config equal in every field to the Effective_Config it yields when the Project_Config_File is absent.
7. THE Build_System SHALL use `@microservices` as the Scope_Default, `packages/microservices` as the microservice Root_Default, `packages/common` as the common Root_Default, and `packages/spa` as the spa Root_Default, so that a project declaring nothing is configured exactly as the Pre_Change_Baseline behaved.
8. THE Build_System SHALL declare each of the Scope_Default and the three Root_Defaults as a literal in exactly one module, and SHALL derive every other use of those values from that module.
9. THE Build_System SHALL read the Project_Config_File at most once per run of a Build_System entry point, and SHALL pass that single Effective_Config value to Package_Discovery, the Repo_Invariant_Checker, the Registry_Generator, the workspace build order derivation, the Project_List derivation, and the Image_Assembler, so that no two components of one run can operate on different configurations.
10. IF the Config_Loader reports one or more Config_Diagnostics, THEN THE Build_System SHALL terminate the run with a non-zero exit status, SHALL report every Config_Diagnostic of that list, SHALL perform no package discovery, write no Microservice_Registry, derive no build order, and assemble no Image_Tree, and SHALL leave the bytes of any already-present Microservice_Registry and generated `Dockerfile` unchanged.
11. THE Build_System SHALL resolve every Discovery_Root and every reported package path against the Project_Directory, and SHALL express every path in its output as a Project_Directory-relative POSIX path.
12. IF a filesystem entry exists at the Project_Config_File path but its contents cannot be read as text, THEN THE Config_Loader SHALL yield no Effective_Config, SHALL report at least one Config_Diagnostic naming that path and the reason it could not be read, and SHALL NOT fall back to the Scope_Default or any Root_Default.

### Requirement 2: Config parsing is a total function reporting diagnostics

**User Story:** As a project author, I want a malformed config to produce a readable list of problems, so that I fix the file rather than debug a stack trace from inside the build tooling.

#### Acceptance Criteria

1. THE Config_Parser SHALL return, for every input string — including the empty string, a string containing no JSON at all, and a string of 1,048,576 characters or more — exactly one of an Effective_Config or a non-empty list of Config_Diagnostics, and SHALL raise no exception and terminate no process for any input string.
2. THE Config_Parser SHALL perform no filesystem access, no network access, no environment-variable read, no clock read, and no random-source read, so that its result is a function of its declared inputs alone, being the input string and the Project_Directory-relative Project_Config_File path it names in its Config_Diagnostics.
3. IF the input string is not parseable as JSON, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:unparsable]` that names the Project_Config_File path and carries non-empty text describing the parse failure, and SHALL return no other Config_Diagnostic for that input.
4. IF the input string parses to a JSON value that is not an object, including a JSON array, string, number, boolean, or null, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:shape]` that names the Project_Config_File path and the JSON type found, and SHALL apply no further validation to that input.
5. IF a recognised key holds a value of the wrong JSON type, being a `scope` that is not a string, a `roots` that is not a JSON object (a JSON array and JSON null each counting as not a JSON object), or a `roots` member that is not a string, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:shape]` per such key that names the key path, the JSON type found, and the JSON type required, and SHALL report no additional Config_Diagnostic concerning a member of a `roots` value that is not a JSON object.
6. IF the input declares a top-level key other than `scope` or `roots`, or a `roots` member other than `microservice`, `common`, or `spa`, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:unknown-key]` per such key that names the key path and lists every recognised key at that position in ascending code-point order, and SHALL continue validating every recognised key of that input, so that a misspelled key fails loudly instead of silently taking a default.
7. THE Config_Parser SHALL, except where criterion 3 or criterion 4 of this requirement requires exactly one Config_Diagnostic, collect every Config_Diagnostic every validation of Requirements 2, 3, and 4 finds for one input before returning, and SHALL return at most one Config_Diagnostic per distinct pair of diagnostic tag and key path, so that one run reports every problem in the file rather than the first and the returned list carries no duplicate entry.
8. THE Config_Parser SHALL order the Config_Diagnostics it returns by ascending code-point comparison of diagnostic tag and then of key path, which given at most one Config_Diagnostic per tag-and-key-path pair is a total order, so that two runs over an identical input string return byte-identical diagnostic text in an identical order.
9. THE Config_Serializer SHALL render every Effective_Config as JSON text that declares all four values, being `scope` and all three `roots` members, declares no other key, and SHALL render two Effective_Configs equal in all four values as byte-identical text.
10. WHEN the Config_Parser is given the string the Config_Serializer produced from an Effective_Config, THE Config_Parser SHALL return an Effective_Config equal to that Effective_Config in all four values and SHALL return no Config_Diagnostic.
11. THE Config_Loader SHALL attempt to read the Project_Config_File exactly once per run, and SHALL distinguish an absent Project_Config_File, reported by no Config_Diagnostic, from a Project_Config_File that exists and cannot be read, reported by the `[config:unreadable]` Config_Diagnostic.
12. IF the Project_Config_File exists and cannot be read, THEN THE Config_Loader SHALL return exactly one Config_Diagnostic tagged `[config:unreadable]` that names the Project_Config_File path and carries non-empty text describing the read failure, SHALL yield no Effective_Config, and SHALL substitute neither the Scope_Default nor any Root_Default for the unread file.
13. THE Config_Parser and the Config_Loader SHALL each return every Config_Diagnostic with all four of its parts present and non-empty, being the bracketed tag, the key path or Project_Config_File path the problem concerns, the offending value or the JSON type found or the underlying failure text, and the reason the value is rejected, and SHALL express every path a Config_Diagnostic carries as a Project_Directory-relative POSIX path.
14. WHEN the Config_Loader has read the Project_Config_File successfully, THE Config_Loader SHALL pass the file's text unmodified to the Config_Parser, and SHALL apply the Filesystem_Validations only IF the Config_Parser returned an Effective_Config, so that no Discovery_Root of a rejected Project_Config_File is probed on the filesystem.

### Requirement 3: Configured_Scope validation

**User Story:** As a project author, I want an unusable scope rejected when I declare it, so that the failure names the field instead of surfacing as an unresolved module hundreds of compilation steps later.

#### Acceptance Criteria

1. THE Config_Parser SHALL accept a declared `scope` value if and only if that value is a Valid_Scope, being `@` followed by one or more characters each of which is a lowercase ASCII letter, an ASCII digit, or a hyphen, and for such a value SHALL report no Config_Diagnostic tagged `[config:scope]` and SHALL set the Effective_Config's Configured_Scope to that value character for character, applying no trimming of surrounding whitespace, no case conversion, and no addition or removal of the leading `@`.
2. IF a declared `scope` value is a string that is not a Valid_Scope, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:scope]` — one per rejected value, not one per offending character — that names the key `scope`, reproduces the rejected value exactly as declared, and states the character set a scope permits, and SHALL return no Effective_Config for that input.
3. THE Config_Parser SHALL reject a declared `scope` value that is the empty string, that consists only of whitespace characters, that carries a leading or trailing whitespace character, that omits the leading `@`, that is exactly `@`, that contains an `@` character at any position other than the first, that contains an uppercase ASCII letter, that contains a `/` character, that contains a `.` or `_` character, or that contains any other character outside the Valid_Scope set, reporting the `[config:scope]` diagnostic of criterion 2 for each such value.
4. IF the `scope` key is present and holds a JSON value that is not a string, THEN THE Config_Parser SHALL apply no Valid_Scope validation to it and SHALL report the `[config:shape]` diagnostic for that key alone, reporting no `[config:scope]` diagnostic for the same key, so that one wrong-typed `scope` yields exactly one diagnostic.
5. IF the Project_Config declares no `scope` key, THEN THE Config_Parser SHALL apply no Valid_Scope validation, SHALL report no `[config:scope]` diagnostic, and SHALL set the Configured_Scope to the Scope_Default.
6. THE Build_System SHALL use the Configured_Scope, and no other value, as the scope of every scoped package name it composes, every Dependency_Specifier prefix it matches, and every import specifier it emits, so that for an Effective_Config whose Configured_Scope differs from the Scope_Default no composed name, matched prefix, or emitted specifier of that run carries the Scope_Default; and THE Build_System SHALL apply this criterion to a run that reached an Effective_Config alone, Requirement 1.10 having terminated every run for which the Config_Loader reported a Config_Diagnostic before any scope was composed, matched, or emitted, so that no run composes a name from a partially validated scope.
7. THE Build_System SHALL compose each Framework_Singleton's package name as the Configured_Scope followed by `/` and that Framework_Singleton's directory name used unchanged, character for character, for each of the four Framework_Singletons, so that one declared scope covers the scaffold's own packages and the project's packages alike.
8. THE Build_System SHALL compare a Dependency_Specifier, a declared package `name`, and a Framework_Singleton name as case-sensitive strings, character for character, with no normalisation of the Configured_Scope or of the compared value.

### Requirement 4: Discovery_Root validation without filesystem access

**User Story:** As a project author, I want a root path that cannot work rejected by shape alone, so that the diagnostic is the same whether or not I have run a build yet.

#### Acceptance Criteria

1. THE Config_Parser SHALL accept a declared `roots` member value if and only if that value is a Valid_Root_Path.
2. IF a declared `roots` member value is not a Valid_Root_Path, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:root-path]` for that member that names the key path, the rejected value, and every one of the Valid_Root_Path conditions the value violates rather than only the first, so that a value violating two conditions yields one diagnostic naming both.
3. THE Config_Parser SHALL validate a declared `roots` member value exactly as it appears in the JSON string, applying no trimming, no separator normalisation, and no case normalisation, and SHALL reject as a Discovery_Root any value that is the empty string, that consists only of whitespace characters, that begins or ends with a whitespace character, that begins with `/`, that ends with `/`, that contains a `\` character, that contains a `*` or `?` character, that contains a `..` path segment, that contains a `.` path segment, or that contains an empty path segment, reporting the `[config:root-path]` diagnostic of criterion 2 for each such value.
4. THE Config_Parser SHALL treat rejecting every value containing a `..` segment as the whole of its escape check, so that no accepted Discovery_Root names a location outside the Project_Directory.
5. IF two Discovery_Roots of the Effective_Config are equal when compared code point for code point, case-sensitively and with no normalisation, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:root-overlap]` for that unordered pair of Consumer_Categories — at most three such diagnostics for the three Discovery_Roots — that names both Consumer_Categories in microservice, common, spa order and the shared path, and that states that a package directly inside a shared root would belong to two Consumer_Categories.
6. IF one Discovery_Root of the Effective_Config lies inside another, meaning the longer path begins with the shorter path followed by a single `/` when compared code point for code point and case-sensitively, THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:root-overlap]` for that unordered pair of Consumer_Categories that names both Consumer_Categories in microservice, common, spa order, both paths, and which root contains which; and THE Config_Parser SHALL return no criterion 6 diagnostic for a pair already reported under criterion 5.
7. IF a Discovery_Root is equal to one of the four Framework_Singleton package directories, lies inside one of them, or contains one of them — each relation determined by the code-point, case-sensitive, single-`/` boundary comparison of criteria 5 and 6 — THEN THE Config_Parser SHALL return exactly one Config_Diagnostic tagged `[config:root-framework]` per offending Consumer_Category and Framework_Singleton directory pair, at most four per Consumer_Category, that names the Consumer_Category, the root path, the Framework_Singleton directory, and which of the three relations holds, and that states that a Framework_Singleton is known by name and is never a discovered package.
8. THE Config_Parser SHALL apply the criterion 5, 6, and 7 checks to every Discovery_Root of the Effective_Config, including a Discovery_Root that took its Root_Default, so that a partially declared `roots` object colliding with a default is rejected.
9. THE Config_Parser SHALL accept a Discovery_Root that is not located under the `packages` directory, since a project's layout is its own choice, and SHALL accept a Valid_Root_Path of any number of path segments, imposing no upper bound on segment count or on total path length and no requirement on any segment's name.
10. IF a declared `roots` member value is rejected by criterion 2 or reported as the wrong JSON type, THEN THE Config_Parser SHALL exclude that member from the criterion 5, 6, and 7 comparisons and SHALL substitute no Root_Default for it, so that no `[config:root-overlap]` or `[config:root-framework]` diagnostic names a value that has already been rejected.
11. THE Config_Parser SHALL return, for one input string, the identical list of Config_Diagnostics whether or not each named Discovery_Root exists on the filesystem, and SHALL report no diagnostic concerning a Discovery_Root's existence, its being a directory, or its being a package, so that every validation of this requirement is decided by the input string alone.

### Requirement 5: Discovery_Root validation against the filesystem

**User Story:** As a project author, I want a root that does not exist or that is itself a package reported by name, so that I learn which of my three roots is wrong.

#### Acceptance Criteria

1. IF no filesystem entry exists at the microservice Discovery_Root path, or an entry exists there whose symbolic-link target is absent, THEN THE Config_Loader SHALL report exactly one Config_Diagnostic tagged `[config:root-missing]` that names the microservice Consumer_Category, the absent path, and the fact that the microservice Discovery_Root must exist, and SHALL yield no Effective_Config, so that the run fails through Requirement 1.10 rather than yielding an empty microservice set, preserving the present handling of an absent microservice container; and THE Config_Loader SHALL report no `[config:root-missing]` diagnostic for a microservice Discovery_Root that resolves to a directory holding no entry, so that an empty microservice root is a discovery result of zero packages rather than a configuration failure.
2. IF the common or the spa Discovery_Root is absent from the filesystem, THEN THE Config_Loader SHALL report no Config_Diagnostic for that Consumer_Category and SHALL yield the Effective_Config carrying that Consumer_Category's Discovery_Root path unchanged, and THE Package_Discovery SHALL yield zero Consumer_Packages for that Consumer_Category and SHALL complete with the same success status it completes with when that root holds one or more packages.
3. ### Requirement 9: Verification of the load-bearing TypeScript settings

## Open Questions Deliberately Deferred

- **The Project_Config_File's filename.** This feature fixes it as `scaffold.config.json`. When the tooling becomes a published package, the spec that publishes it may rename the file; nothing in this feature depends on the name beyond the single literal of Requirement 1.1.
- **One scope or two.** This feature has exactly one Configured_Scope, covering the Framework_Singletons and the project's own packages alike (Requirement 3.7), which is correct while both live in one repository under one scope. Separating the platform's own fixed scope from the project's configured scope belongs to the spec that publishes the platform packages.
- **Whether a types-only package needs to ship into a runtime image.** Unchanged and still open. `packages/contracts` is built and staged for every Selector exactly as before.

## Accepted Imprecisions

- **The Registry_Template carries a scope literal.** The root `prepare` script copies a committed template before anything is compiled, so no compiled generator can write it. This feature does not make the template generated; it adds the `[scope:template]` checks of Requirements 8.9 and 8.10, which turn a silent compile failure for a project that changed its scope into a named failure at the next `check:invariants` run. The template becomes generated output when the registry moves into the consuming project, which is a later spec.
- **The scope-literal check of Requirement 12.4 covers `packages/build-tools/src/` only.** A package manifest must declare its scoped `name` as a literal, because npm requires a literal, and documentation and test sources legitimately mention a scope. Widening the check would produce false positives, and a false positive on a build gate is worse than the drift it would catch. The Build_System's own sources are where a surviving literal would silently defeat the configuration, so that is where the check applies.
- **The Emit_Script reads JSON with POSIX sh.** It runs before any install and cannot use a JSON parser. Requirement 4's Valid_Root_Path restrictions are what keep the values it must read extractable without one: a Valid_Root_Path is a single-line, quote-free, unescaped string. A Project_Config_File whose JSON is valid but unusually formatted may therefore be readable by the Config_Parser and not by the Emit_Script, and Requirement 11.7 makes that case a named failure rather than a silently wrong `Dockerfile`.
