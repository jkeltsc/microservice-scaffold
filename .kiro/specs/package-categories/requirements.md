# Requirements Document

## Introduction

The scaffold currently has no explicit taxonomy of package kinds. Everything under `packages/` is either "the Overseer", "the microservices namespace", or "something a manifest-shape heuristic decides about". `packages/build-tools/src/shared-packages.ts` `classify()` decides shared-package membership by reading each candidate's `package.json`: an `@microservices`-scoped `name` plus both `main` and `types`, with the Overseer excluded by name and the `microservices` directory excluded by name. Two exclusions in that scheme are incidental rather than intended: `build-tools` falls out only because it declares no `main`/`types`, and `integration-tests` falls out only because its name is not `@microservices`-scoped. Adding a `main`/`types` pair to `build-tools` would silently turn a bin-only tooling package into a discovered shared package that gets compiled and staged into every container image. The classification is also silent in the other direction: a genuinely shared library that forgets its barrel fields simply disappears from discovery, from the build order, and from the image, with no diagnostic.

This feature replaces that heuristic with an explicit taxonomy whose organizing axis is **framework versus consumer**, not "shared versus not shared". The framework tier is the scaffold itself — `packages/contracts/`, `packages/overseer/`, `packages/build-tools/`, `packages/integration-tests/` — and the Build_System knows those packages **by name**. The consumer tier is what a user of this template writes, and the Build_System discovers those packages **by location**: each consumer package is a direct subdirectory of a Namespace_Container that names its category. The single rule to remember is: *the framework knows its own parts by name; it discovers the consumer's parts by location.*

Three consumer categories exist after this change. `packages/microservices/` is the existing category, unchanged in location. `packages/common/` is a new category for consumer-written shared libraries; the existing sample shared package `packages/config/` moves to `packages/common/config/`. `packages/spa/` is a new category for bundler-built frontend packages, which are built through their own `npm run build` and never as roots of `tsc --build`; this feature adds the category and the tooling support for it and creates no Spa_Package content.

`packages/contracts/` is promoted out of the discovered set and into the framework tier. Today it re-enters the image as a required shared dependency like any other shared library. After this change it behaves like the Overseer: known by name, always built, always first in build order, always staged. Whether a types-only package needs to ship into a runtime image at all is a separate question that this feature deliberately leaves open; staging behavior for `contracts` is unchanged here.

The feature is a build-system and repository-architecture refactor. It changes no runtime behavior: the Overseer mounts the same microservices at the same paths, the generated Microservice_Registry statically imports the same selected microservices, and the toggle variables are untouched. Both shipped container configurations continue to build and to contain the same microservice and Overseer surface as before.

## Glossary

- **Build_System**: The tooling that discovers packages, generates the Microservice_Registry, orders the workspace build, derives the Project_List, and assembles the container Image_Tree. Concretely `packages/build-tools/` plus `scripts/emit-effective-dockerfile.sh`.
- **Package_Category**: The kind a workspace package belongs to. Exactly one of the Framework tier or one of the Consumer_Categories.
- **Framework_Singleton**: A workspace package that is part of the scaffold itself and is known to the Build_System **by name**, never discovered. The complete set is `packages/contracts/`, `packages/overseer/`, `packages/build-tools/`, and `packages/integration-tests/`.
- **Consumer_Category**: A kind of package a user of the template writes, discovered **by location** as a direct subdirectory of that category's Namespace_Container. The complete set is Microservice_Package (`packages/microservices/`), Common_Package (`packages/common/`), and Spa_Package (`packages/spa/`).
- **Namespace_Container**: The single directory whose direct subdirectories are the packages of one Consumer_Category: `packages/microservices/`, `packages/common/`, `packages/spa/`. A Namespace_Container is not itself a package and declares no `package.json`.
- **Microservice_Package**: A Consumer_Category package at `packages/microservices/<identifier>/` that exports a Microservice_Path and an Express router. Its directory name is its Microservice_Identifier.
- **Common_Package**: A Consumer_Category package at `packages/common/<name>/`: a consumer-written leaf library imported by package name (`@microservices/<name>`) by one or more Microservice_Packages and/or the Overseer. Replaces the previous "Shared_Package" concept for consumer-written libraries.
- **Spa_Package**: A Consumer_Category package at `packages/spa/<name>/`: a standalone bundler-built frontend package whose build output is produced by a bundler (such as Vite) through the package's own `npm run build`. A Spa_Package exposes no importable API: its build output is a directory of bundled static assets consumed at runtime by whatever serves them, so no Tsc_Project imports a Spa_Package and no Spa_Package is a compile-time prerequisite of any package. Distinct from a SPA source directory kept *inside* a Microservice_Package, which is that microservice's private implementation detail and is not a Spa_Package.
- **Consumer_Package**: Any package belonging to a Consumer_Category.
- **Build_Kind**: How a package's build output is produced. Exactly one of Tsc_Project or Bundler_Project.
- **Tsc_Project**: A package compiled by the TypeScript solution builder, eligible to appear as a root of `tsc --build`.
- **Bundler_Project**: A package built by invoking its own `npm run build`, never eligible as a root of `tsc --build`.
- **Tsc_Build_Pass**: The single `tsc --build` invocation over the ordered Tsc_Project roots a Selector justifies. The first of the two build phases.
- **Bundler_Build_Phase**: The `npm run build` invocations, one per Spa_Package in the Required_Dependencies, each run with that Spa_Package's own directory as its working directory. The second of the two build phases, entered only after the Tsc_Build_Pass has exited with status zero.
- **Barrel**: A package's `index.ts` re-export surface, declared in its manifest through `main` and `types`, and the only stable public API of the package.
- **Package_Name_Lookup**: The mapping from a discovered Consumer_Package's directory to the package `name` declared in its own `package.json`. A lookup used to resolve dependency specifiers — not a membership gate.
- **Dependency_Specifier**: An `@microservices`-scoped key of a package's `dependencies`, e.g. `@microservices/config`.
- **Selector**: The `MICROSERVICES` build/runtime value: `*` (or blank) for every discovered Microservice_Package, or a comma-separated list of Microservice_Identifiers.
- **Selected_Microservices**: The Microservice_Packages resolved from the Selector.
- **Required_Dependencies**: The **build set**: the discovered Consumer_Packages that the Selected_Microservices and the Overseer need, reached transitively by following `@microservices`-scoped dependencies from those roots. Every member of the Required_Dependencies is built. Membership in the Required_Dependencies does not by itself justify staging a package into the Image_Tree; the staging subset is the Staged_Dependencies.
- **Staged_Dependencies**: The **stage set**: the subset of the Required_Dependencies reachable from the Selected_Microservices and the Overseer by a traversal that follows `@microservices`-scoped Dependency_Specifiers but does not expand the outgoing Dependency_Specifiers declared by a Spa_Package. The traversal may **arrive at** a Spa_Package — a Spa_Package reached from those roots is itself a member of the Staged_Dependencies, because its bundled assets are what a runtime serves — but the traversal does not **continue through** it, so a Consumer_Package reachable only by way of a Spa_Package is not a member. Every member of the Staged_Dependencies is present in the Image_Tree. Staged_Dependencies is always a subset of Required_Dependencies. Membership is a property of the paths that reach a package, not a label on the package: a Common_Package reached both directly from a Selected_Microservice and by way of a Spa_Package is a member.
- **Framework_Constants_Module**: The single module in `packages/build-tools/src/` that declares every Framework_Singleton name and directory and every Namespace_Container directory, and is the only place in the Build_System where those literals appear.
- **Image_Tree**: The staging tree the image assembler writes (`/out`) and the container runtime stage overlays.
- **Image_Assembler**: `buildImageTree` in `packages/build-tools/src/image-tree.ts`.
- **Package_Discovery**: The Build_System component that enumerates Consumer_Packages per Consumer_Category (today `packages/build-tools/src/shared-packages.ts`).
- **Dependency_Resolver**: The Build_System component that computes the Required_Dependencies in topological order and the Staged_Dependencies subset of them (today `requiredSharedPackages`).
- **Integrity_Assertion**: A post-assembly check that fails the build when the Image_Tree contains a package the selection does not justify.
- **Build_Watcher**: The TypeScript solution builder running in watch mode inside the Dev_Server, which incrementally recompiles the Project_List on source change and signals each completed compile pass.
- **Dev_Server**: The `npm run dev` supervisor in `packages/build-tools/src/dev-supervisor.ts` that derives the Project_List, runs the Build_Watcher, and owns the Overseer child process.
- **Project_List**: The ordered list of root projects the Dev_Server hands to the TypeScript solution builder (`projectListFrom` / `devProjectList` in `packages/build-tools/src/dev-supervisor.ts`).
- **Emit_Script**: `scripts/emit-effective-dockerfile.sh`, which renders the committed `Dockerfile.template` into the generated `Dockerfile`.
- **Manifest_Copy_Block**: The generated block of per-workspace `package.json` `COPY` lines the Emit_Script writes at both `# --- MANIFEST_COPY_* ---` anchors.
- **Exclusion_List**: The Emit_Script's by-name list of top-level `packages/` entries that contribute no `COPY` line. Currently expressed inline in the script's single `awk` pass (`name == "integration-tests" || name == "microservices"`) and referred to as `EXCLUDE_TOPLEVEL` in the Steering_Documents.
- **Workspace_Build_Order**: The topological order the Build_System **derives** over every workspace package — the four Framework_Singletons and every discovered Consumer_Package — from the `@microservices`-scoped `dependencies` each of those packages declares in its own `package.json`, in which every package precedes each package that declares a Dependency_Specifier resolving to it. It is the order in which the repository-wide build invokes each workspace package's own `build` script. Distinct from the entry order of the Root_Manifest's `workspaces` array, which carries no build-order meaning, and broader than the Selector-scoped Tsc_Project roots of Requirement 6, which cover only what a Selector justifies and exclude `packages/build-tools` and `packages/integration-tests`.
- **Workspace_Coverage**: The Root_Manifest obligation that every Framework_Singleton directory and every Consumer_Package directory is matched by exactly one entry of the `workspaces` array, which is what npm needs in order to discover the workspaces. An obligation over the *set* of entries only: it constrains their order in no way.
- **Bootstrap_Build**: The compilation of exactly `packages/contracts` and `packages/build-tools`, performed before any Build_System step that is itself compiled output can run. The pattern `scripts/common-startup.js` already uses, and the reason the repository-wide build can compute a Workspace_Build_Order that compiled tooling derives.
- **Root_Manifest**: The repository root `package.json`, which declares the `workspaces` array, the shared devDependencies, and the `engines` block. Its `workspaces` array is subject to Workspace_Coverage, and the entry order of that array carries no build-order meaning.
- **Repository**: The checked-in contents of this template repository: its committed files and directories, as distinct from any build output or container image produced from them.
- **Pre_Change_Baseline**: The repository state at the commit immediately preceding this feature, used as the reference for "unchanged behavior" comparisons.
- **Overseer**: The Framework_Singleton at `packages/overseer/`: the routing frontend application that mounts each enabled Microservice_Package's router at that microservice's declared Microservice_Path.
- **Microservice_Registry**: The generated TypeScript manifest the Build_System writes for a given Selector, which statically imports the Selected_Microservices and is consumed by the Overseer at build time.
- **Generic_Container**: An image built with Selector `*`.
- **Specific_Container**: An image built with the Selector `microservice1,microservice2`.
- **Steering_Documents**: `.kiro/steering/structure.md` and `.kiro/steering/tech.md`.

## Requirements

### Requirement 1: The framework/consumer taxonomy and its discovery rule

**User Story:** As a scaffold maintainer, I want an explicit taxonomy of package kinds with one discovery rule per tier, so that a package's category is a deliberate declaration rather than a side effect of the shape of its manifest.

#### Acceptance Criteria

1. THE Build_System SHALL assign every workspace package located under `packages/` that a pattern of the Root_Manifest's `workspaces` array matches to exactly one Package_Category, being either the Framework_Singleton tier or exactly one of the three Consumer_Categories Microservice_Package, Common_Package, and Spa_Package, so that no such package is assigned to two Package_Categories and no such package is assigned to none.
2. THE Build_System SHALL determine Framework_Singleton membership solely from the package name and package directory literals declared in the Framework_Constants_Module, which declare exactly the four Framework_Singletons `contracts`, `overseer`, `build-tools`, and `integration-tests`.
3. THE Build_System SHALL determine Consumer_Category membership from the package directory location alone, assigning a direct subdirectory of `packages/microservices/` to Microservice_Package, a direct subdirectory of `packages/common/` to Common_Package, and a direct subdirectory of `packages/spa/` to Spa_Package.
4. IF a directory is located two or more levels below a Namespace_Container, THEN THE Package_Discovery SHALL exclude that directory from the discovered Consumer_Packages of every Consumer_Category and treat it as private content of the Consumer_Package that is its nearest ancestor direct subdirectory of that Namespace_Container.
5. THE Package_Discovery SHALL classify a Consumer_Package using only the package directory's path relative to `packages/`, reading no field of that package's `package.json` to decide the classification.
6. THE Package_Discovery SHALL exclude all four Framework_Singletons from the discovered Consumer_Packages of every Consumer_Category, so that no package appears both in the Framework_Singleton set and in a Consumer_Category set.
7. THE Repository SHALL contain, as direct subdirectories of `packages/`, only the four Framework_Singleton directories and the three Namespace_Container directories declared in the Framework_Constants_Module, and no other directory, as a convention that code review upholds and that no Build_System check validates.
8. WHEN a Consumer_Package directory is added as a direct subdirectory of a Namespace_Container, THE Build_System SHALL include that Consumer_Package in the discovered set of that Consumer_Category on the next build, with no edit to `Dockerfile.template`, to any existing Consumer_Package, or to any registration list in the Build_System sources.
9. IF a direct subdirectory of `packages/` is neither a Framework_Singleton directory nor a Namespace_Container directory declared in the Framework_Constants_Module, THEN THE Build_System SHALL assign that directory no Package_Category, SHALL exclude that directory from every Consumer_Category's discovered set, and SHALL complete the build with a zero exit status, treating the directory as neither an error nor a warning.
10. IF an entry directly inside a Namespace_Container is not a directory, THEN THE Package_Discovery SHALL exclude that entry from the discovered Consumer_Packages of that Consumer_Category and complete discovery successfully.

### Requirement 2: Replace manifest-based classification with location-based discovery

**User Story:** As a scaffold maintainer, I want the manifest-shape classifier removed, so that adding a `main` field to a tooling package cannot silently change what ships in a container image.

#### Acceptance Criteria

1. THE Package_Discovery SHALL enumerate Common_Packages as exactly one Common_Package per qualifying direct subdirectory entry of `packages/common/`, and SHALL enumerate no Common_Package for any entry nested deeper than one level below `packages/common/`.
2. THE Package_Discovery SHALL enumerate Spa_Packages as exactly one Spa_Package per qualifying direct subdirectory entry of `packages/spa/`, and SHALL enumerate no Spa_Package for any entry nested deeper than one level below `packages/spa/`.
3. THE Package_Discovery SHALL enumerate Microservice_Packages as exactly one Microservice_Package per qualifying direct subdirectory entry of `packages/microservices/`, and SHALL enumerate no Microservice_Package for any entry nested deeper than one level below `packages/microservices/`.
4. THE Package_Discovery SHALL treat a direct entry of a Namespace_Container as a qualifying entry when the entry resolves to a directory and the entry name does not begin with `.`, and SHALL ignore every other direct entry, including regular files.
5. THE Package_Discovery SHALL return the discovered Consumer_Packages of each Consumer_Category ordered by ascending code-point comparison of directory name, so that two runs over an unchanged filesystem return identical sequences in identical order.
6. IF the `packages/common/` or `packages/spa/` Namespace_Container directory is absent from the filesystem, or is present and contains zero qualifying entries, THEN THE Package_Discovery SHALL yield zero Consumer_Packages for that Consumer_Category, raise no error, and complete with the same success status it completes with when the directory holds one or more qualifying entries.
7. IF the `packages/microservices/` directory is absent from the filesystem, THEN THE Package_Discovery SHALL fail the run with an error naming the missing directory and SHALL return no discovery result for any Consumer_Category, preserving the current handling rather than yielding an empty set.
8. THE Package_Discovery SHALL decide Consumer_Category membership using only the candidate's Namespace_Container location and its directory name, consulting the `name`, `main`, `types`, `bin`, and `dependencies` fields of no candidate manifest.
9. THE Build_System SHALL assign a package the same Package_Category whether or not that package's manifest declares `main` or `types`, so that adding or removing either field changes neither the discovered Consumer_Packages of any Consumer_Category nor the set of packages staged into an Image_Tree for a given Selector.
10. WHERE a Framework_Singleton manifest such as `packages/build-tools/package.json` declares both `main` and `types`, THE Package_Discovery SHALL discover no Consumer_Package for that Framework_Singleton directory in any Consumer_Category.

### Requirement 3: Package_Name_Lookup for dependency resolution

**User Story:** As a scaffold user, I want dependency specifiers to resolve through each package's declared name, so that the name a consumer imports is always the name the depended-on package actually declares.

#### Acceptance Criteria

1. WHEN Package_Discovery enumerates the direct subdirectories of a Namespace_Container, THE Package_Discovery SHALL read the `name` field declared in each discovered Consumer_Package's own `package.json` and record that exact declared string, with no trimming, case folding, or other normalization, as that package's single Package_Name_Lookup entry keyed by the package's repo-relative directory.
2. THE Dependency_Resolver SHALL resolve a Dependency_Specifier to a Consumer_Package only when the specifier and a Package_Name_Lookup entry value are equal character for character as case-sensitive strings, with no prefix, alias, version-range, or path-based matching.
3. THE Build_System SHALL use a Package_Name_Lookup entry for a Consumer_Package, or a Framework_Constants_Module name for a Framework_Singleton, as the sole source of every name a Dependency_Specifier is resolved against, and SHALL derive no resolvable package name from a directory name.
4. IF a discovered Consumer_Package's `package.json` is absent, unreadable, or not parseable as JSON, THEN THE Package_Discovery SHALL terminate with a non-zero exit status and an error identifying the offending package's repo-relative directory and which of those three conditions occurred, and SHALL produce no Package_Name_Lookup, no generated Microservice_Registry, no Project_List, and no Image_Tree.
5. IF a discovered Consumer_Package's `package.json` declares no `name`, declares a `name` that is not a string, or declares a `name` that is empty or whitespace only, THEN THE Package_Discovery SHALL terminate with a non-zero exit status and an error identifying the offending package's repo-relative directory and indicating that the declared name is missing or empty.
6. IF a discovered Consumer_Package of any of the three Consumer_Categories, including a Microservice_Package, declares a `name` that is not equal, character for character and case-sensitively, to `@microservices/` followed by that package's directory name, THEN THE Package_Discovery SHALL terminate with a non-zero exit status and an error identifying the offending package's repo-relative directory, the declared name, and the expected name, because a Microservice_Package whose declared name diverges from its directory name is npm-linked under the declared name while the generated Microservice_Registry imports the directory-derived name and the Image_Assembler stages the package at the directory-derived path, so the divergence has no valid outcome and this check reports it at discovery rather than as an unresolved-module `tsc` failure.
7. THE Dependency_Resolver SHALL resolve a Dependency_Specifier that equals a Framework_Singleton name declared in the Framework_Constants_Module, compared as a case-sensitive string, without failing and without that Framework_Singleton appearing in any Consumer_Category's discovered set, and SHALL add no Framework_Singleton to the Required_Dependencies.
8. IF a Dependency_Specifier matches neither a Package_Name_Lookup entry nor a Framework_Singleton name declared in the Framework_Constants_Module, THEN THE Dependency_Resolver SHALL terminate with a non-zero exit status and an error identifying the repo-relative directory of the declaring package and the unresolved specifier, and SHALL produce no Required_Dependencies, no Project_List, and no Image_Tree.
9. IF two or more discovered Consumer_Packages record the same Package_Name_Lookup value, THEN THE Package_Discovery SHALL terminate with a non-zero exit status and an error identifying the duplicated name and the repo-relative directory of every package declaring it.
10. THE Dependency_Resolver SHALL treat only `@microservices`-scoped `dependencies` keys as Dependency_Specifiers, and SHALL ignore every other `dependencies` key without attempting resolution and without failing.

### Requirement 4: Barrel validation per Consumer_Category

**User Story:** As a scaffold user, I want a missing barrel in a library package to be a loud build failure, so that a typo in a manifest does not silently remove a library from the build order and the image.

#### Acceptance Criteria

1. IF a discovered Common_Package's `package.json` does not declare both `main` and `types` as non-empty strings, THEN THE Package_Discovery SHALL fail the build with a non-zero exit status and an error naming the offending package directory and each of `main` and `types` that is absent, empty, or not a string.
2. WHERE a discovered package is a Spa_Package, THE Package_Discovery SHALL complete discovery successfully whether the package declares both, one, or neither of `main` and `types`, applying no Barrel validation to that package.
3. IF a discovered Spa_Package's `package.json` does not declare a `build` entry in `scripts` whose value is a non-empty string, THEN THE Package_Discovery SHALL fail the build with a non-zero exit status and an error naming the offending package directory and the missing `build` script.
4. THE Package_Discovery SHALL apply the criterion 1 Barrel validation to every discovered Common_Package and the criterion 3 build-script validation to every discovered Spa_Package, with no per-package exemption list and no per-package override in any manifest, environment variable, or Build_System source.
5. THE Package_Discovery SHALL apply to a discovered Microservice_Package the Requirement 3.6 name mirroring validation, being a validation separate from the two this requirement defines, and SHALL apply to that Microservice_Package neither the criterion 1 Barrel validation nor the criterion 3 build-script validation, and SHALL preserve the current handling of a Microservice_Package that is not a usable module, whose failure surfaces from the subsequent `tsc` build on the generated static import rather than from discovery.
6. THE Package_Discovery SHALL apply neither the criterion 1 Barrel validation nor the criterion 3 build-script validation to any Framework_Singleton, so that a bin-only Framework_Singleton declaring neither `main` nor `types` completes discovery successfully.
7. WHERE more than one discovered Consumer_Package violates criterion 1 or criterion 3 in a single run, THE Package_Discovery SHALL report every offending package directory in lexicographic order of directory name within one failure, so that repeated runs over an unchanged filesystem produce identical output.
8. IF the Package_Discovery fails a run for a criterion 1 or criterion 3 violation, THEN THE Build_System SHALL emit no Microservice_Registry, no Project_List, and no Image_Tree for that run, and SHALL leave every previously written build output unmodified.

### Requirement 5: Promote `contracts` to a Framework_Singleton

**User Story:** As a scaffold maintainer, I want `contracts` treated as part of the framework rather than as a discovered library, so that the scaffold's own type surface is not subject to consumer-package discovery rules.

#### Acceptance Criteria

1. THE Build_System SHALL treat `packages/contracts/` as a Framework_Singleton, determined solely by the package name and package directory declared for it in the Framework_Constants_Module, with no field of the `packages/contracts/package.json` participating in that determination.
2. THE Package_Discovery SHALL exclude `packages/contracts/` from the discovered Consumer_Packages of every Consumer_Category, by Framework_Singleton name taken from the Framework_Constants_Module, regardless of which fields the package's `package.json` declares.
3. THE Dependency_Resolver SHALL exclude `packages/contracts/` from the Required_Dependencies for every Selector value, including when a Selected_Microservice or the Overseer declares a Dependency_Specifier naming `@microservices/contracts`, so that the returned Required_Dependencies contain no entry for `packages/contracts/`.
4. THE Image_Assembler SHALL include `packages/contracts/` as a root of its `tsc --build` invocation for every Selector value, including a Selector that resolves to exactly one Microservice_Package and a Selector under which no other built package declares a Dependency_Specifier naming `@microservices/contracts`.
5. THE Image_Assembler SHALL order `packages/contracts/` as the first entry among the roots of its `tsc --build` invocation, ahead of every other Tsc_Project and therefore ahead of every Tsc_Project that declares a Dependency_Specifier naming it, for every Selector value.
6. THE Image_Assembler SHALL stage `packages/contracts/` into the Image_Tree at `node_modules/@microservices/contracts` as a real directory, not a workspace symlink, holding the package's `package.json` and its compiled output directory, for every Selector value.
7. THE Dependency_Resolver SHALL resolve a Dependency_Specifier of `@microservices/contracts` declared by any Consumer_Package or by the Overseer to the `packages/contracts/` Framework_Singleton, without reporting an unresolved Dependency_Specifier and without adding an entry to the Required_Dependencies.
8. FOR ANY Selector value, THE Image_Assembler SHALL stage under `node_modules/@microservices/contracts` a set of tree-relative file paths equal to the set staged for `packages/contracts/` before this change for that same Selector, namely the package's `package.json` plus every file of its compiled output directory, with no file added and no file omitted.
9. IF the `packages/contracts/` build exits with a non-zero status, or its compiled output directory is absent or empty when staging begins, THEN THE Image_Assembler SHALL fail the build with an error naming `packages/contracts/` and indicating that the Framework_Singleton produced no compiled output, and SHALL leave the Image_Tree without a `node_modules/@microservices/contracts` entry.
10. THE Integrity_Assertion SHALL accept the `node_modules/@microservices/contracts` entry of the Image_Tree as justified by Framework_Singleton membership rather than by being a required dependency, for every Selector value.

### Requirement 6: Build_Kind per Package_Category and build order

**User Story:** As a scaffold user, I want each category built the way that category is meant to be built, so that a bundler-built frontend package can live in the monorepo without being fed to `tsc --build`.

#### Acceptance Criteria

1. THE Build_System SHALL assign Build_Kind Tsc_Project to every Framework_Singleton, every Microservice_Package, and every Common_Package, determined by Package_Category alone and independent of every field declared in that package's `package.json`.
2. THE Build_System SHALL assign Build_Kind Bundler_Project to every Spa_Package, determined by Package_Category alone and independent of every field declared in that package's `package.json`.
3. THE Image_Assembler SHALL pass as the roots of its `tsc --build` invocation exactly the Tsc_Projects the Selector justifies, namely `packages/contracts/`, every Common_Package in the Required_Dependencies, every Selected_Microservice, and the Overseer, and SHALL pass no Spa_Package as a root for any Selector value.
4. THE Image_Assembler SHALL build each Spa_Package that is a member of the Required_Dependencies by invoking that package's own `npm run build` exactly once, with that Spa_Package's own directory as the working directory of the invocation.
5. THE Image_Assembler SHALL invoke the `npm run build` of each Spa_Package in the Required_Dependencies, being the Bundler_Build_Phase, only after the Tsc_Build_Pass has exited with status zero.
6. THE Image_Assembler SHALL order the roots of its `tsc --build` invocation so that `packages/contracts/` is first, every Tsc_Project precedes each Tsc_Project that declares a Dependency_Specifier naming it, the Overseer is last, and each root appears exactly once.
7. THE Image_Assembler SHALL produce, for repeated runs over an unchanged filesystem and an unchanged Selector, an identical ordered root list and an identical set of Spa_Package build invocations.
8. THE Image_Assembler SHALL stage, for each staged package of every Package_Category including Spa_Package, exactly that package's own `package.json` plus the complete contents of that package's `dist/` directory, and no other file from that package's source tree.
9. IF a required Spa_Package's `npm run build` cannot be executed or exits with a non-zero status, THEN THE Image_Assembler SHALL stage no package, SHALL fail with an error naming the offending package directory and the observed exit status, and SHALL terminate with a non-zero status.
10. IF the `tsc --build` invocation exits with a non-zero status, THEN THE Image_Assembler SHALL stage no package, SHALL fail with an error indicating that the TypeScript build failed, and SHALL terminate with a non-zero status.
11. IF a package the Image_Assembler is about to stage has no `dist/` directory after its build has completed, THEN THE Image_Assembler SHALL fail with an error naming the offending package directory and the missing build output, and SHALL terminate with a non-zero status.
12. WHERE a Common_Package is a member of the Required_Dependencies reached only through a Spa_Package, and no Selected_Microservice and neither the Overseer nor any other Tsc_Project declares a Dependency_Specifier resolving to that Common_Package, THE Image_Assembler SHALL pass that Common_Package as a root of the Tsc_Build_Pass, so that the Common_Package's compiled output exists before the Bundler_Build_Phase begins.
13. THE Image_Assembler SHALL treat no Spa_Package as a prerequisite of the Tsc_Build_Pass, for every Selector value, because no Tsc_Project imports a Spa_Package.
14. THE Image_Assembler SHALL decide membership among the roots of its `tsc --build` invocation from the Required_Dependencies and SHALL decide staging into the Image_Tree from the Staged_Dependencies, so that a Common_Package which is a member of the Required_Dependencies and not a member of the Staged_Dependencies is a root of the Tsc_Build_Pass whose compiled output the Image_Assembler copies into no entry of the Image_Tree.

### Requirement 7: Minimality and integrity per Consumer_Category

**User Story:** As an operator, I want a Specific_Container to ship only the packages its selected microservices actually need, so that image minimality holds for every category by construction.

#### Acceptance Criteria

1. 8. 14. WHERE a workspace package declares a Dependency_Specifier resolving to another workspace package, THE Build_System SHALL make the resolved package's compiled output present under `node_modules` before it invokes the declaring package's `build` script, so that the declaring package's plain `tsc` invocation resolves the specifier through `node_modules` without a `tsc --build` project reference.
15. THE Root_Manifest SHALL satisfy Workspace_Coverage by matching each Framework_Singleton directory and each Consumer_Package directory with exactly one `workspaces` entry, counting a glob entry as matching every direct subdirectory of its Namespace_Container.
16. THE Build_System SHALL derive no build-order meaning from the entry order of the Root_Manifest's `workspaces` array, so that reordering that array's entries without changing the set of directories they match changes neither the Workspace_Build_Order nor the outcome of the repository-wide build.
17. THE Build_System SHALL provide an automated check, executed as part of `npm run ci`, that reads the `workspaces` array of the Root_Manifest and the workspace package directories present in the Repository, exits with a zero status when Workspace_Coverage holds for every workspace package, and exits with a non-zero status when one or more workspace packages fail to satisfy Workspace_Coverage.
18. 19. WHERE a workspace package declares a Dependency_Specifier resolving to a workspace package that the same single `workspaces` entry also matches, THE automated check SHALL exit with a zero status, applying no ordering rule to the `workspaces` array and reporting no violation.
20. WHERE a `workspaces` glob entry matches no directory on the filesystem, THE automated check SHALL treat that entry as matching zero workspace packages and exit with a zero status.
21. THE Root_Manifest's `build` script, its `pretest` step, and the build step of its `ci` script SHALL each build every workspace package in the Workspace_Build_Order.
22. WHEN `npm start` or `npm run dev` runs, THE Build_System SHALL perform its existing Bootstrap_Build and its existing Selector-scoped Project_List derivation unchanged, and THE Workspace_Build_Order SHALL alter neither the set nor the order of the projects either command builds.

## Open Questions Deliberately Deferred

- Whether `packages/contracts/`, being a types-only package, needs to ship into runtime images at all. This feature keeps shipping it (Requirement 5.6, 5.8) and records the question (Requirement 15.8).

## Accepted Imprecisions

- The Build_System requires a Spa_Package's build output to be self-contained (Requirement 9.12) but verifies that obligation through no mechanical check. Scanning a Spa_Package's `dist/` for surviving `@microservices/` specifiers was considered and deliberately rejected: such a specifier can appear in a source map or in a string literal in the SPA's own source, both of which are harmless, so the scan would produce false positives, and a false positive on a build gate is a worse outcome than the risk the gate guards against. A Spa_Package whose bundler is configured to externalize a workspace dependency therefore fails at runtime rather than at build time, and keeping the bundler configured to inline its workspace dependencies is the Spa_Package author's responsibility.
